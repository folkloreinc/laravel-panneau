# 0005: Auth modes and guards

- Status: accepted
- Date: 2026-10-14

## Context

Laravel side of the [shared auth decision](https://github.com/folkloreinc/panneau-js/blob/v5.x/docs/decisions/0012-authentication.md). v1 calls Fortify's `AuthenticatedSessionController` directly, and relies on the app having configured Fortify, including its login view. Many sites already use Fortify, or another system, for their public users.

## Decision

- **`auth.mode` setting:**
  - **`panneau`:** the package registers its own auth routes under its prefix.
  - **`external`:** the site handles login. The package only checks the guard and the `viewPanneau` gate, and its definition points unauthenticated users to `auth.login_url`.
- **Guard.** `auth.guard` selects the guard. `panneau:install` can create a separate `panneau` guard, with its own user provider and table, for sites whose public users must stay apart from admins.
- **Fortify as a library.** The package uses Fortify's actions and features (2FA, passkeys, password reset, email verification) through its own controllers. It doesn't use Fortify's routes, views or global configuration, so the site's own Fortify setup is untouched.
- **OAuth providers** use Socialite, a suggested dependency, as described in #34:
  - allowed email domains;
  - Google's `hd` claim;
  - no automatic user creation unless the project provides a resolver.
- **Features** are toggled in `config('panneau.auth')`: password, providers, reset, two-factor, passkeys, email verification.

## Consequences

- Adding Panneau to a site with members doesn't change how members log in.
- Projects stop configuring Fortify views for the admin.
